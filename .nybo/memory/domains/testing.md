## [TEST-01] Live/dev environment — dockerized backend+db+frontend
- **What**: local dev stack runs via `make up` (`docker compose up --build`) — services `db` (Postgres 16), `backend` (FastAPI/uvicorn, `--reload`, bind-mounts `./src` and `./tests`), `frontend` (Vite, bind-mounts `./src/frontend`).
- **Reach it**: backend at `http://localhost:8000` (OpenAPI at `/openapi.json`, docs at `/docs`); frontend at `http://localhost:5173`. `docker ps` to confirm containers are up before assuming a cold start is needed — `backend`'s `--reload` picks up source edits live, no rebuild needed for a Python-only change.
- **Auth**: `POST /auth/registro` `{email, password, nombre?}` → 201; `POST /auth/login` `{email, password}` → `{access_token, token_type}`. Use `Authorization: Bearer <access_token>` on every subsequent call. No seeded/fixture users — register fresh ones per smoke run.
- **Seeding data preexisting-to-a-fix directly in Postgres**: `docker exec gastos-test-db-1 psql -U taskia -d taskia -c "<SQL>"`. `rolenum` enum values are uppercase (`ADMIN`/`MEMBER`), not lowercase, despite the Python-side `RolEnum` values being lowercase strings — SQLAlchemy maps the Python enum *member name* to the Postgres enum label, not the Python value.
- **Cold start** (if containers are down): `make up` (or `docker compose up --build`) from repo root, using `.env` copied from `.env.example`. `make migrate` applies migrations against the running `db` service if needed.
- **Backend test command**: `.venv/bin/python -m pytest tests/` (or `make test` inside the container). Frontend: `npm run test` (vitest), `npm run build` (tsc + vite build), `npm run lint` (eslint on `src/frontend`).
- Discovered during `/nybo-verify --auto` for `fix-membresia-duplicada-actor-2026-09-14` (2026-09-14) — `stack.yaml`'s `dev_runbook` had no `cold_start`/`smoke` recorded yet; recommend `/nybo-brownfield-bootstrap --runbook` to formalize this into `stack.yaml` itself.

## [TEST-02] Live smoke from a git worktree conflicts on host ports with the main checkout's own `make up`
- **What**: `docker-compose.yml`'s `backend`/`frontend` ports (`8000`/`5173`) are hardcoded, no env override. Compose names containers from the *directory* name (`docker-compose.yml`'s project name defaults to the basename of the directory it runs from) — the main checkout (`gastos-test`) and each `.claude/worktrees/<branch>` checkout get DIFFERENT container name prefixes but try to publish the SAME host ports. If the main checkout's `make up` is already running (a human's own active dev session — confirmed live: `gastos-test-backend-1`/`gastos-test-frontend-1` running throughout this spec's BUILD), a worktree's own `docker compose up` fails with `port is already allocated` on `backend` — `db` alone succeeds since it publishes no host port in the base file.
- **Never tear down or reuse the main checkout's stack to route around this** — it's very likely someone's live dev session, and even if not, its bind-mounted source is the MAIN branch's code, not the worktree's — attaching to it would smoke-test the wrong diff (fixture-backed-evidence risk, not this cycle's own change).
- **Workaround that worked**: write a throwaway `docker-compose.override.yml` (auto-merged by `docker compose`) at the worktree root remapping only the port(s) actually needed — e.g. `{db: {ports: ["5433:5432"]}}` — then `docker compose up -d db` (skip `backend`/`frontend` containers entirely) and run the backend as a plain local process instead: `DATABASE_URL=postgresql+psycopg2://taskia:taskia@127.0.0.1:<published-port>/taskia python3 -m uvicorn src.api.main:app --host 127.0.0.1 --port <free-port>` (this project's own venv/system Python already has every backend dependency `pytest` needs, confirmed live). Delete the override file and `docker compose down` when done — the override is never committed, and `down` also removes the worktree-local volume, so no persisted data survives between cycles.
- **Gotcha inside the workaround**: `ports:` merges by CONCATENATION across `-f base -f override`, not replacement — remapping a port already published in the base file (e.g. trying to override `backend`'s `8000:8000`) still leaves the original mapping in `docker compose config`, and the conflict persists. Only add a `ports:` override for a service that has NONE in the base file (this project's `db`) — for a service that already publishes a port, this override technique doesn't work at all; route around it by not running that service's container (as above) rather than trying to override its port.
